# Agent instructions for this repo

This repository is a **process guide** for spec-driven development, not an application. Cursor and Claude Code installs are in [docs/install.md](docs/install.md).

- Do not scaffold an app unless the user explicitly asks for one.
- Keep the README on the method (specs, plan files, tasks, verify). Host file locations belong in [docs/install.md](docs/install.md).
- Put per-change work under `docs/specs/<change-id>/` using `_template/` (human starter). The layout always includes `docs/system/`, including `glossary.md`. Spark and ideas seed a thin landscape when that folder is missing and do not rewrite an existing one. They fill a missing `glossary.md` when the folder already exists. Intake writes the landscape, including `glossary.md`, and does not skip it. An existing glossary is left alone. Skills also carry copies in their `assets/`; keep both in sync.
- Keep [docs/install.md](docs/install.md) and [plugins/crav1/README.md](plugins/crav1/README.md) current when install or first-run steps change.
- When adding or updating a crav1 skill/agent, edit `.cursor/skills/crav1/crav1-<name>/` (agents: `.cursor/agents/crav1-<name>.md`, templates: that skill’s `assets/` and `.cursor/agent-assets/crav1-<name>/`), then run `scripts/sync-crav1-plugin.sh` so `plugins/crav1/` and the generated `.claude/` tree match. `scripts/sync-crav1-claude.sh --check` fails if `.claude/` is stale. See `.cursor/rules/kit-maintainer.mdc`.
- From a one-sentence spark, use `/crav1-spark-to-spec` then `/crav1-tighten-spec`. Works greenfield or as a feature on an existing repo (new spec slug unless they said extend). When `docs/system/` is missing, it seeds a thin landscape from the repo, including `glossary.md`, then writes the spec, then adds one index row. An existing landscape is not rewritten. A missing `glossary.md` is filled when the folder already exists. An existing glossary is left alone. Do not code first. Brownfield: `/crav1-feature-branch` prompts `feat/<slug>` (default) or specify-only `spec/<slug>` before writing files (no push, no PR).
- From a pile of ideas plus technical hunches, use `/crav1-ideas-to-spec` (paste one unstructured blob; diagrams + ADRs + chosen export). When `docs/system/` is missing, it seeds a thin landscape the same way, including `glossary.md`, then the spec, then one index row. A missing `glossary.md` is filled when the folder already exists. An existing glossary is left alone. Do not code first. Several v0 features or several repos: `/crav1-intake-to-specs` instead.
- From mixed files (notes, diagrams, screenshots, optional code as context), use `/crav1-intake-to-specs`. Writes `docs/system/`, including `glossary.md`, plus one spec per v0 feature. When that folder already exists and `glossary.md` is missing, it writes only that file. An existing glossary is left alone. After Index, it prompts `/crav1-finalize-commit` (does not commit itself). Later features: spark or ideas with `@docs/system/`, new slug. Do not code first.
- From repos that already make up a system, plus a dump to match, use `/crav1-match-to-specs`. Asks where the spec files go, then writes `docs/system/`, including `glossary.md`, and one spec per confirmed slice (done, partial, or not in the code). When that folder already exists, it only fills gaps the match needs, including a missing `glossary.md`. An existing glossary is left alone. Does not replace intake, spark, or ideas. Does not plan, implement, or commit. A slice that is not in the code is not planned by that command.
- A later dump, when specs already exist, is `/crav1-match-dump-to-specs`. It reads the spec folders (skip `_template`) and does not ask for a slug first. It sorts the dump into belongs to this spec, already in that spec, or does not fit, and writes new bits only after that sort is confirmed. It does not create a slug. Leftovers stay listed. It reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not seed `docs/system/` when that folder is missing. A missing `glossary.md` is filled only when `docs/system/` already exists. An existing glossary is left alone. It does not plan, implement, or commit.
- A code change that already landed, when specs already exist, is `/crav1-code-into-specs`. No dump is required. The change is a commit, a commit range, or the diff of the current branch against the default branch. If the user does not name one, it looks at git and asks with options only (recent commits, or the branch diff) and does not ask for a typed hash. It reads the spec folders (skip `_template`) and does not ask for a slug first. It sorts the change into belongs to this spec, already described there, or fits none of them, and writes what belongs only after that sort is confirmed, the same way `/crav1-add-to-spec` writes a quote. It does not create a slug. Leftovers stay listed. It reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not seed `docs/system/` when that folder is missing. A missing `glossary.md` is filled only when `docs/system/` already exists. An existing glossary is left alone. It does not invent a landscape from the diff. It does not plan, implement, or commit. It does not watch the repo. It runs only when someone points it at a change. Point at `/crav1-finalize-commit` only if those spec edits should be committed.
- New information for one existing spec is `/crav1-add-to-spec`. It adds that information to `spec.md`, then reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not create a glossary. A missing glossary row that the new information defines can be one of those listed edits. It does not plan, implement, or commit. Tighten stays for mushy wording.
- When `/crav1-spark-to-spec`, `/crav1-ideas-to-spec`, or `/crav1-intake-to-specs` creates a new spec folder and the git remote is Azure Repos, it asks once whether to link an Azure Boards work item. If the user replies with an id, it writes `docs/specs/<slug>/work-item.md` as `Work item: <id>`. Intake lists the new slugs in that one question. Skip writes nothing and does not ask again in that run. GitHub and other hosts are not asked. Creating the work item in Azure Boards is out of scope. Do not call Azure DevOps or pass `--work-items`.
- Critique with `/crav1-architecture-reviewer`, then `/crav1-tighten-spec` one issue at a time (option to get a suggestion).
- After tightening, `/crav1-resolve-questions` to keep or answer each remaining Open question.
- When the spec is accepted, `/crav1-plan-from-spec` writes `plan.md` and `tasks.md`. Do not code in that step. Optional: `/crav1-review-plan` then `/crav1-tighten-plan` (plan `P#`s only; do not edit `spec.md`).
- Build with `/crav1-implement-task` (one `T#` per turn) or `/crav1-complete-task` (isolated worker for that `T#` through commit → verify → optional fix). Several `T#`s on **one** spec: `/crav1-complete-tasks`. Several **specs**, one after another: `/crav1-complete-features` (serial `feat/<slug>` from default; not parallel). Persist commit style as a rule (same as finalize-commit onward) before the first worker. Prove a slice alone with `/crav1-verify-spec`. Before **live** verify (Aspire/API host, compose, browser localhost), refresh the running resource per `crav1-verify-spec` `references/live-host.md`; do not mark pass on a stale host.
- After `/crav1-verify-spec`, `/crav1-fix-from-verify` with **no Gap** walks the inner-loop queue: verify failed → claimed/unverified → `G#`. Not unimplemented tasks. Do not edit `spec.md`. `/crav1-fix-live` is the same queue with a live-path hint.
- Prefer editing the spec or plan over long patch-prompt threads when implementation drifts.
- For a paste-ready GitKraken Summary/Description, `/crav1-draft-commit-message`. It asks `style.md` vs live git log, this commit only vs onward (writes a host persist rule — Cursor `.cursor/rules/draft-commit-style.mdc` or `draft-commit-gitlog.mdc`, Claude Code `.claude/rules/` or `~/.claude/rules/` with the same stems; delete that file to undo). Do not commit unless they asked. When `docs/specs/<slug>/work-item.md` exists, the mention is the last description line.
- To change the wording and then `git commit` (no push) or copy for GitKraken, `/crav1-finalize-commit` (`commit` is the first/top choice). Keep that mention through the HEAD check and the Cursor-attribution strip.
- To push the change branch and open one pull request (no merge, no commit), `/crav1-open-pr`. Push only after an explicit yes. GitHub uses `gh`; Azure DevOps uses `az repos pr create` when the CLI is available; otherwise it prints commands and GitKraken GUI paste fields. On Windows, pass a multi-line Azure DevOps description as `--description "@<file>"` (UTF-8 without BOM) so `cmd.exe` does not keep only the first line, then delete the file. Quote `--query` values that contain parentheses. Workers stay no push / no PR. Add a Work item section only when `work-item.md` exists. Do not pass `--work-items`. Merging is `/crav1-merge-pr` in a later turn, and only when that turn names the pull request.
- To merge one named pull request, `/crav1-merge-pr`. Only when this turn explicitly asks (number or URL). Always a merge commit: `gh pr merge --merge`, or `az repos pr update --org <url> --id <n> --status completed --squash false --detect false` (Azure DevOps treats that as no-fast-forward). Re-read the pull request after complete (the update response can still say active) and require `status` completed. Count parents with `git rev-list --parents -n 1` on `lastMergeCommit.commitId`. Do not trust `lastMergeCommit.parents` (it can be null). If git cannot see the commit, GET the commits API and count `parents`, or say the merge type could not be verified. One parent stops the skill. If `az` is missing, the update fails, or a branch policy disallows that merge type, print the REST PATCH and the web UI steps. Do not squash, rebase, bypass policy, delete the branch unless asked, or change work-item links.
