# Agent instructions for this repo

This repository is a **process guide** for spec-driven development, not an application. Cursor and Claude Code installs are in [docs/install.md](docs/install.md).

- Do not scaffold an app unless the user explicitly asks for one.
- Keep the README on the method (specs, plan files, tasks, verify). Host file locations belong in [docs/install.md](docs/install.md).
- Put per-change work under `docs/specs/<change-id>/` using `_template/` (human starter). The layout always includes `docs/system/`, including `glossary.md`. Spark and ideas seed a thin landscape when that folder is missing and do not rewrite an existing one except new glossary rows and the picture update. They fill a missing `glossary.md` when the folder already exists. Intake writes the landscape, including `glossary.md`, and does not skip it. New glossary rows are appended. Existing rows are not rewritten. The picture update adds what is new to the short description, the diagram, and how the parts connect, and does not rewrite what is already there. A meaning the source does not state is `to be researched`. Skills also carry copies in their `assets/`; keep both in sync.
- Keep [docs/install.md](docs/install.md) and [plugins/crav1/README.md](plugins/crav1/README.md) current when install or first-run steps change.
- When adding or updating a crav1 skill/agent, edit `.cursor/skills/crav1/crav1-<name>/` (agents: `.cursor/agents/crav1-<name>.md`, templates: that skill’s `assets/` and `.cursor/agent-assets/crav1-<name>/`), then run `scripts/sync-crav1-plugin.sh` so `plugins/crav1/` and the generated `.claude/` tree match. `scripts/sync-crav1-claude.sh --check` fails if `.claude/` is stale. See `.cursor/rules/kit-maintainer.mdc`.
- From a one-sentence spark, use `/crav1-spark-to-spec` then `/crav1-tighten-spec`. Works greenfield or as a feature on an existing repo (new spec slug unless they said extend). When `docs/system/` is missing, it seeds a thin landscape from the repo, including `glossary.md`, then writes the spec, then adds one index row. An existing landscape is not rewritten. A missing `glossary.md` is filled when the folder already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. Do not code first. Brownfield: `/crav1-feature-branch` prompts `feat/<slug>` (default) or specify-only `spec/<slug>` before writing files (no push, no PR).
- From a pile of ideas plus technical hunches, use `/crav1-ideas-to-spec` (paste one unstructured blob; diagrams + ADRs + chosen export). When `docs/system/` is missing, it seeds a thin landscape the same way, including `glossary.md`, then the spec, then one index row. A missing `glossary.md` is filled when the folder already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. Do not code first. Several v0 features or several repos: `/crav1-intake-to-specs` instead.
- From mixed files (notes, diagrams, screenshots, optional code as context), use `/crav1-intake-to-specs`. Writes `docs/system/`, including `glossary.md`, plus one spec per v0 feature. When that folder already exists and `glossary.md` is missing, it writes only that file. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. After Index, it prompts `/crav1-finalize-commit` (does not commit itself). Later features: spark or ideas with `@docs/system/`, new slug. Do not code first.
- From repos that already make up a system, plus a dump to match, use `/crav1-match-to-specs`. Asks where the spec files go, then writes `docs/system/`, including `glossary.md`, and one spec per confirmed slice (done, partial, or not in the code). When that folder already exists, it only fills gaps the match needs, including a missing `glossary.md`. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. Does not replace intake, spark, or ideas. Does not plan, implement, or commit. A slice that is not in the code is not planned by that command.
- A later dump, when specs already exist, is `/crav1-match-dump-to-specs`. It reads the spec folders (skip `_template`) and does not ask for a slug first. It sorts the dump into belongs to this spec, already in that spec, or does not fit, and writes new bits only after that sort is confirmed. It does not create a slug. Leftovers stay listed. It reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not seed `docs/system/` when that folder is missing. A missing `glossary.md` is filled only when `docs/system/` already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. It does not plan, implement, or commit.
- A code change that already landed, when specs already exist, is `/crav1-code-into-specs`. No dump is required. The change is a commit, a commit range, or the diff of the current branch against the default branch. If the user does not name one, it looks at git and asks with options only (recent commits, or the branch diff) and does not ask for a typed hash. It reads the spec folders (skip `_template`) and does not ask for a slug first. It sorts the change into belongs to this spec, already described there, or fits none of them, and writes what belongs only after that sort is confirmed, the same way `/crav1-add-to-spec` writes a quote. It does not create a slug. Leftovers stay listed. It reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not seed `docs/system/` when that folder is missing. A missing `glossary.md` is filled only when `docs/system/` already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. It does not invent a landscape from the diff. It does not plan, implement, or commit. It does not watch the repo. It runs only when someone points it at a change. Point at `/crav1-finalize-commit` only if those spec edits should be committed.
- New information for one existing spec is `/crav1-add-to-spec`. It adds that information to `spec.md`, then reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not create a glossary. A new glossary row can be one of those listed edits and is not written unless apply is chosen. A meaning the new information does not state is `to be researched`. Existing rows are not rewritten. It does not plan, implement, or commit. Tighten stays for mushy wording.
- When `/crav1-spark-to-spec`, `/crav1-ideas-to-spec`, or `/crav1-intake-to-specs` creates a new spec folder and the git remote is Azure Repos, it asks once whether to link an Azure Boards work item. If the user replies with an id, it writes `docs/specs/<slug>/work-item.md` as `Work item: <id>`. Intake lists the new slugs in that one question. Skip writes nothing and does not ask again in that run. GitHub and other hosts are not asked. Creating the work item in Azure Boards is out of scope. Do not call Azure DevOps or pass `--work-items`.
- Critique with `/crav1-architecture-reviewer`, then `/crav1-tighten-spec` one issue at a time (option to get a suggestion). Architecture review may name `/crav1-security-review` as an optional next step. It does not run it.
- When architecture already exists, `/crav1-security-review` asks whether the thing in front of it is secure. The same command covers the whole system, one existing spec, or the change in front of us. If the target is unclear, it asks with options only, one option per real target already in front of it. It does not invent an architecture. Findings are risks and what should change. It does not write exploit steps. It shows the findings, one confirm, then writes only the kept findings (`docs/system/security.md` for a system pass, or a Security section on that spec for a feature or a change). It does not plan, implement, or commit. Name `/crav1-finalize-commit` when a file changed. Do not run it. Spark, plan, and verify do not run this command.
- `/crav1-repos-to-spec` is cross-cutting. The user names one or more repos. It reads those repos and writes one architecture spec the lanes can extend at `docs/architecture/spec.md` when that file is missing. The folder is `docs/architecture/`. The file is `spec.md`. That path is locked. It stays out of `docs/system` and out of `docs/specs`. Do not invent any other folder. `docs/specs` stays one folder per feature slug. `docs/system` stays the short picture. When a real note is already in `docs/system/`, it does not rewrite those notes and writes the missing architecture spec and `docs/architecture/left-out.md`. When `docs/architecture/spec.md` is already there, a later re-read adds only what is new and does not rewrite lines that are already there. It also reads `docs/architecture/left-out.md` and removes a line when the code shows it. The same rule applies to system notes that are already there. When those notes are missing, it writes the `docs/system/` notes `/crav1-explain` reads. A fact the code shows is confirmed. Before any file is written, it confirms in sections, one question each: one per named repo, inferred guesses, links, and left-out. Every item stays listed. A guess stays out of the spec until that section accepts it, and then it is accepted from a guess, not a code fact. A guess that stays left out is written to `docs/architecture/left-out.md`. The left-out answer can accept a line, keep it left out, or dismiss it. Dismiss means it is not offered again. A link between repos is written only when the code shows it. If none is found, it says so. It does not invent links. Confirming a guess does not turn it into a link. It does not design the next feature, write application code, or start Specify, Plan, or Build. It is not `/crav1-code-into-specs`. It does not plan, implement, or commit. Name `/crav1-finalize-commit` when a file changed. Do not run it.
- `/crav1-explain` is cross-cutting. It reads the system notes already in `docs/system/`. The first answer is a short TLDR. If the user says longer, it goes one level deeper from the same notes. The user can point it at one part. The user can ask whether the system can do something. If the notes say yes, say yes and point at where. If they say no, say no. If they never mention it, say that is not written down. It does not guess, invent a second document, teach, or start Specify, Plan, or Build. If the picture is older than the specs, say so and name `/crav1-keep-current`. Do not run it.
- `/crav1-keep-current` is cross-cutting. It updates that same picture when something was added: the short description, the diagram, and how the parts connect. It adds what is new and does not rewrite what is already there. It does not design the change and does not build it. It can be run on its own. The same passes that already append a new glossary row (spark, ideas, intake, match, and any sibling that already does that append) also run this picture update. They do not rewrite existing glossary rows. Name `/crav1-finalize-commit` when a file changed. Do not run it.
- After tightening, `/crav1-resolve-questions` to keep or answer each remaining Open question.
- When the spec is accepted, `/crav1-plan-from-spec` writes `plan.md` and `tasks.md`. Do not code in that step. Each task verify note names the checks. The plan also says whether this repo has a linter or checker for the code those tasks will touch. When it has one, the plan names it and Build is expected to leave that check green. When it does not, the plan says so and stops before Build. The user decides to add the linter or to go on without one. Do not install one. Specify stays yes/no acceptance and does not name the linter. Optional: `/crav1-review-plan` then `/crav1-tighten-plan` (plan `P#`s only; do not edit `spec.md`). Those two use the same linter rule when they check that a plan is complete.
- Build with `/crav1-implement-task` (one `T#` per turn) or `/crav1-complete-task` (isolated worker for that `T#` through commit → verify → optional fix). Several `T#`s on **one** spec: `/crav1-complete-tasks`. Several **specs**, one after another: `/crav1-complete-features` (serial `feat/<slug>` from default; not parallel). Persist commit style as a rule (same as finalize-commit onward) before the first worker. Prove a slice alone with `/crav1-verify-spec`. Before **live** verify (Aspire/API host, compose, browser localhost), refresh the running resource per `crav1-verify-spec` `references/live-host.md`; do not mark pass on a stale host.
- After `/crav1-verify-spec`, `/crav1-fix-from-verify` with **no Gap** walks the inner-loop queue: verify failed → claimed/unverified → `G#`. Not unimplemented tasks. Do not edit `spec.md`. `/crav1-fix-live` is the same queue with a live-path hint.
- Prefer editing the spec or plan over long patch-prompt threads when implementation drifts.
- For a paste-ready GitKraken Summary/Description, `/crav1-draft-commit-message`. It asks CRAV1 style vs live git log, this commit only vs onward (writes a host persist rule — Cursor `.cursor/rules/draft-commit-style.mdc` or `draft-commit-gitlog.mdc`, Claude Code `.claude/rules/` or `~/.claude/rules/` with the same stems; delete that file to undo). Do not commit unless they asked. When `docs/specs/<slug>/work-item.md` exists, the mention is the last description line.
- To change the wording and then `git commit` (no push) or copy for GitKraken, `/crav1-finalize-commit` (`commit` is the first/top choice). Keep that mention through the HEAD check and the Cursor-attribution strip.
- To push the change branch and open one pull request (no merge, no commit), `/crav1-open-pr`. Push only after an explicit yes. GitHub uses `gh`; Azure DevOps uses `az repos pr create` when the CLI is available; otherwise it prints commands and GitKraken GUI paste fields. On Windows, pass a multi-line Azure DevOps description as `--description "@<file>"` (UTF-8 without BOM) so `cmd.exe` does not keep only the first line, then delete the file. Quote `--query` values that contain parentheses. Workers stay no push / no PR. Add a Work item section only when `work-item.md` exists. Do not pass `--work-items`. It may name `/crav1-review-pr` as an optional next step and does not run it. Merging is `/crav1-merge-pr` in a later turn, and only when that turn names the pull request.
- To name a real bug that already exists, `/crav1-fix-bug`. Only when this turn names one. A real bug is a verify failure on work that is already shipping, or a defect that comes in from outside. If none is named, it stops. It does not go hunting. A design gap found before Build stays in the spec. An unfinished task stays a task. A one-off flaky check is a note, unless it keeps blocking ship. It says where the bug was seen (verify, a report, or production), names the bug, points at the spec or the shipped behavior it breaks, and names the lane. A spec miss goes to Specify. A plan miss goes to Plan. A verify miss or a broken implementation goes to Build. It does not start that lane, edit code, open a pull request, or create an Azure Boards work item. It is not a lane and not a stretch of verify. When the user asks for startup options, it is one of the options in that list. It is an intake for a bug that already exists. It is not a skill that runs because a repo is new, and it is not started automatically. Spark, specify, plan, and verify do not run it.
- To review one named open pull request, `/crav1-review-pr`. Only when this turn names it (number or URL) or clearly asks to review that pull request. Any open pull request, not only a feature branch. If none is named, ask which one and stop. Do not pick the newest. It reads the diff. Spec, plan, `verify.md`, the pull request body, and a required green linter must hold before it says ship. Each miss is its own finding (what is off, what could happen, decision ship, fix, or drop). Any fix or drop means it does not say ship. It names the lane and does not start it. A body mismatch stays on that pull request. It does not edit code, the spec, or the plan. It does not run the tests, vote, post a comment, install a linter, change branch protection, or merge. Suggestions do not block ship. A secret in the diff is a first-section fix. A clean review says so and stops. Spark, specify, and verify do not run it. A review is not a merge ask.
- To merge one named pull request, `/crav1-merge-pr`. Only when this turn explicitly asks (number or URL). Always a merge commit: `gh pr merge --merge`, or `az repos pr update --org <url> --id <n> --status completed --squash false --detect false` (Azure DevOps treats that as no-fast-forward). Re-read the pull request after complete (the update response can still say active) and require `status` completed. Count parents with `git rev-list --parents -n 1` on `lastMergeCommit.commitId`. Do not trust `lastMergeCommit.parents` (it can be null). If git cannot see the commit, GET the commits API and count `parents`, or say the merge type could not be verified. One parent stops the skill. If `az` is missing, the update fails, or a branch policy disallows that merge type, print the REST PATCH and the web UI steps. Do not squash, rebase, bypass policy, delete the branch unless asked, or change work-item links. Do not run `/crav1-review-pr`. A review is not a merge ask. This command still stops when a required host check is red.
