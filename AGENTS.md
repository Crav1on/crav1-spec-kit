# Agent instructions for this repo

This repository is a **process guide** for spec-driven development, not an application. Cursor and Claude Code installs are in [docs/install.md](docs/install.md).

- When the user asks for startup options, name only these seven: `/crav1-spark-to-spec`, `/crav1-ideas-to-spec`, `/crav1-intake-to-specs`, `/crav1-match-to-specs`, `/crav1-repos-to-spec`, `/crav1-environment-read`, and `/crav1-fix-bug`. Every other skill is a later skill. That ask names the list. It does not run a skill and does not move work into a lane. Each starter still follows the rules it already has. `/crav1-repos-to-spec` still runs only when the user names repos. `/crav1-environment-read` still runs only when the user names the host. Naming production, prod, or live stops. `/crav1-fix-bug` still runs only when the user names a real bug.
- Do not scaffold an app unless the user explicitly asks for one.
- Keep the README on the method (specs, plan files, tasks, verify). Host file locations belong in [docs/install.md](docs/install.md).
- Put per-change work under `docs/specs/<change-id>/` using `_template/` (human starter). The layout always includes `docs/system/`, including `glossary.md`. Spark and ideas seed a thin landscape when that folder is missing and do not rewrite an existing one except new glossary rows and the picture update. They fill a missing `glossary.md` when the folder already exists. Intake writes the landscape, including `glossary.md`, and does not skip it. New glossary rows are appended. Existing rows are not rewritten. The picture update adds what is new to the short description, the diagram, and how the parts connect, and does not rewrite what is already there. A meaning the source does not state is `to be researched`. `docs/system/repos.md` has a per-repo `Synced at` column, `<branch>@<short sha>, <date>`. A repo may list several branches, separated by `; `. Example: `main@abc1234, 2026-10-07; develop@def5678, 2026-10-06`. When `/crav1-keep-current`, `/crav1-repos-to-spec`, `/crav1-code-into-specs`, or `/crav1-intake-to-specs` and `/crav1-ideas-to-spec` (where they read repos) read a whole repo, they set that repo's column to the branch and commit they actually read. They touch only the repos they read. When a run reads only one slice, it does not touch the repo column. It writes or updates `Synced at: <repo> <branch>@<short sha>, <date>` in that slice's `spec.md`. A consumer measuring drift uses the older of the repo column and the slice line, and an empty value means unknown, so fall back to spec file commit dates. Skills also carry copies in their `assets/`; keep both in sync.
- Keep [docs/install.md](docs/install.md) and [plugins/crav1/README.md](plugins/crav1/README.md) current when install or first-run steps change.
- When adding or updating a crav1 skill/agent, edit `.cursor/skills/crav1/crav1-<name>/` (agents: `.cursor/agents/crav1-<name>.md`, templates: that skill’s `assets/` and `.cursor/agent-assets/crav1-<name>/`), then run `scripts/sync-crav1-plugin.sh` so `plugins/crav1/` and the generated `.claude/` tree match. `scripts/sync-crav1-claude.sh --check` fails if `.claude/` is stale. See `.cursor/rules/kit-maintainer.mdc`.
- From a one-sentence spark, use `/crav1-spark-to-spec` then `/crav1-tighten-spec`. Works greenfield or as a feature on an existing repo (new spec slug unless they said extend). When `docs/system/` is missing, it seeds a thin landscape from the repo, including `glossary.md`, then writes the spec, then adds one index row. An existing landscape is not rewritten. A missing `glossary.md` is filled when the folder already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. Do not code first. Brownfield: `/crav1-feature-branch` prompts `feat/<slug>` (default) or specify-only `spec/<slug>` before writing files (no push, no PR).
- From a pile of ideas plus technical hunches, use `/crav1-ideas-to-spec` (paste one unstructured blob; diagrams + ADRs + chosen export). When `docs/system/` is missing, it seeds a thin landscape the same way, including `glossary.md`, then the spec, then one index row. A missing `glossary.md` is filled when the folder already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. Do not code first. Several v0 features or several repos: `/crav1-intake-to-specs` instead.
- From mixed files (notes, diagrams, screenshots, optional code as context), use `/crav1-intake-to-specs`. Writes `docs/system/`, including `glossary.md`, plus one spec per v0 feature. When that folder already exists and `glossary.md` is missing, it writes only that file. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. After Index, it prompts `/crav1-finalize-commit` (does not commit itself). Later features: spark or ideas with `@docs/system/`, new slug. Do not code first.
- From repos that already make up a system, plus a dump to match, use `/crav1-match-to-specs`. Asks where the spec files go, then writes `docs/system/`, including `glossary.md`, and one spec per confirmed slice (done, partial, or not in the code). When that folder already exists, it only fills gaps the match needs, including a missing `glossary.md`. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. Does not replace intake, spark, or ideas. Does not plan, implement, or commit. A slice that is not in the code is not planned by that command.
- A later dump, when specs already exist, is `/crav1-match-dump-to-specs`. It reads the spec folders (skip `_template`) and does not ask for a slug first. It sorts the dump into belongs to this spec, already in that spec, or does not fit, and writes new bits only after that sort is confirmed. It does not create a slug. Leftovers stay listed. It reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not seed `docs/system/` when that folder is missing. A missing `glossary.md` is filled only when `docs/system/` already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. It does not plan, implement, or commit.
- A code change that already landed, when specs already exist, is `/crav1-code-into-specs`. No dump is required. The change is a commit, a commit range, or the diff of the current branch against the default branch. If the user does not name one, it looks at git and asks with options only (recent commits, or the branch diff) and does not ask for a typed hash. It reads the spec folders (skip `_template`) and does not ask for a slug first. It sorts the change into belongs to this spec, already described there, or fits none of them, and writes what belongs only after that sort is confirmed, the same way `/crav1-add-to-spec` writes a quote. It does not create a slug. Leftovers stay listed. It reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. A whole-repo read sets that repo's `Synced at` cell. A one-slice read writes the slice line and does not touch the column. That stamp is not an apply option. It does not seed `docs/system/` when that folder is missing. A missing `glossary.md` is filled only when `docs/system/` already exists. New glossary rows are appended. Existing rows are not rewritten. A meaning the source does not state is `to be researched`. It does not invent a landscape from the diff. It does not plan, implement, or commit. It does not watch the repo. It runs only when someone points it at a change. Point at `/crav1-finalize-commit` only if those spec edits should be committed.
- New information for one existing spec is `/crav1-add-to-spec`. It adds that information to `spec.md`, then reports whether `docs/system/` or another spec has to change, and edits those other files only if the user chooses apply. It does not create a glossary. A new glossary row can be one of those listed edits and is not written unless apply is chosen. A meaning the new information does not state is `to be researched`. Existing rows are not rewritten. It does not plan, implement, or commit. Tighten stays for mushy wording. A kept addition from `/crav1-meeting-to-specs` is handed here. The impact check still runs. The environment-read and suggest-tests-for-code handoffs ask once at the end of the run, not per item, whether to run `/crav1-keep-current`, and do not run it.
- When `/crav1-spark-to-spec`, `/crav1-ideas-to-spec`, or `/crav1-intake-to-specs` creates a new spec folder and the git remote is Azure Repos, it asks once whether to link an Azure Boards work item. If the user replies with an id, it writes `docs/specs/<slug>/work-item.md` as `Work item: <id>`. Intake lists the new slugs in that one question. Skip writes nothing and does not ask again in that run. GitHub and other hosts are not asked. Creating the work item in Azure Boards is out of scope. Do not call Azure DevOps or pass `--work-items`.
- Critique with `/crav1-architecture-reviewer`, then `/crav1-tighten-spec` one issue at a time (option to get a suggestion). Architecture review may name `/crav1-security-review` as an optional next step. It does not run it.
- When architecture already exists, `/crav1-security-review` asks whether the thing in front of it is secure. The same command covers the whole system, one existing spec, or the change in front of us. If the target is unclear, it asks with options only, one option per real target already in front of it. It does not invent an architecture. Findings are risks and what should change. It does not write exploit steps. It shows the findings, one confirm, then writes only the kept findings (`docs/system/security.md` for a system pass, or a Security section on that spec for a feature or a change). It does not plan, implement, or commit. Name `/crav1-finalize-commit` when a file changed. Do not run it. Spark, plan, and verify do not run this command.
- `/crav1-repos-to-spec` is cross-cutting. The user names one or more repos. It reads those repos and writes one architecture spec the lanes can extend at `docs/architecture/spec.md` when that file is missing. The folder is `docs/architecture/`. The file is `spec.md`. That path is locked. It stays out of `docs/system` and out of `docs/specs`. Do not invent any other folder. `docs/specs` stays one folder per feature slug. `docs/system` stays the short picture. When a real note is already in `docs/system/`, it does not rewrite those notes except the `Synced at` cell of a repo this run read, and writes the missing architecture spec and `docs/architecture/left-out.md`. When `docs/architecture/spec.md` is already there, a later re-read adds only what is new and does not rewrite lines that are already there, except that `Synced at` cell. It also reads `docs/architecture/left-out.md` and removes a line when the code shows it. The same rule applies to system notes that are already there. When those notes are missing, it writes the `docs/system/` notes `/crav1-explain` reads. A fact the code shows is confirmed. Before any file is written, it confirms in sections, one question each: one per named repo, inferred guesses, links, and left-out. Every item stays listed. A guess stays out of the spec until that section accepts it, and then it is accepted from a guess, not a code fact. A guess that stays left out is written to `docs/architecture/left-out.md`. The left-out answer can accept a line, keep it left out, or dismiss it. Dismiss means it is not offered again. A link between repos is written only when the code shows it. If none is found, it says so. It does not invent links. Confirming a guess does not turn it into a link. It does not design the next feature, write application code, or start Specify, Plan, or Build. It is not `/crav1-code-into-specs`. It does not plan, implement, or commit. Name `/crav1-finalize-commit` when a file changed. Do not run it.
- `/crav1-environment-read` is cross-cutting. The user names the host at the start. Examples: Azure, AWS, Google Cloud. It still runs only when the user names the host. Naming production, prod, or live stops. It does not guess the host. It never reads production data. One pass reads every non-prod environment. Each seen line keeps its own environment. Each host has its own reader. A host with no reader stops and says so. It does not pretend to read it. This build has readers for Azure, AWS, and Google Cloud. Any other host stops with no reader. It does not read Azure DevOps, GitHub, or CI. The user names the host, not the subscription, the account, or the project. Marks come from the name, the group, the tags, and `docs/environments/marks.md` when that file exists. Non-prod words include dev, test, stage, uat, and qa. Pre-prod, a resource shared with prod, and a prod-only resource are shape and connections only, after one yes. Prod-only means the only mark is production. A no lists them as not read, and a declined prod-only resource stays skipped. A line from that yes says `prod only`. What is still unmarked can be marked from shown evidence, a group suggestion, or by the user. The skill appends only confirmed lines to `docs/environments/marks.md`. It does not write `docs/system`, `docs/architecture/spec.md`, feature specs, or `docs/architecture/left-out.md`. A fact is marked as seen in that environment, not as something the code shows. It does not become a link unless the environment actually shows the connection. A trigger is a connection. The line shows the definition, not a payload or a secret. After the first read, and before any section, it can look inside a database or storage when the user says yes. SQL is metadata only. Storage is structure only. It never reads a row or a blob. Production databases and production storage are never opened. A prod-only shape read does not open them. A database with no clear environment is asked before it is opened. It does not install a tool, and it does not create a login, a firewall rule, a role, or a key. If the CLI or the login is missing, the stop names which. Confirmation is one section at a time, with its own question and answer, and nothing is dropped to keep a section short. After the user confirms a section, the skill that already owns the file adds only what is new. System facts go to `docs/system`. Architecture facts go to `docs/architecture/spec.md`. A slice Match already owns goes on that feature spec. A left-out line the environment now shows comes off `docs/architecture/left-out.md`. It does not rewrite lines that are already there. It does not start Specify, Plan, or Build. After `docs/environments/marks.md` lines are added, it asks once whether to run `/crav1-keep-current` and does not run that refresh from the question. Name `/crav1-finalize-commit` when a file changed. Do not run it. `/crav1-explain` is cross-cutting. It reads the system notes already in `docs/system/`. The first answer is a short TLDR. If the user says longer, it goes one level deeper from the same notes. The user can point it at one part. The user can ask whether the system can do something. If the notes say yes, say yes and point at where. If they say no, say no. If they never mention it, say that is not written down. It does not guess, invent a second document, teach, or start Specify, Plan, or Build. On every run it compares the feature index with each slice's node in `docs/system/diagrams.md` and its line in `## How the parts connect`. Names match only by slug, spec title, or main resource name. At the end it lists each slice that is missing entirely or partly, including done and retired, with status, and names `/crav1-keep-current`. Do not run it. When the picture has nothing on the question, quote the first paragraph of the matching slice's spec, labelled as coming from the spec, and name `/crav1-whats-known-about`. When no spec matches either, say so and name that skill. Do not run it.
- `/crav1-pipeline-environments` is cross-cutting. The user names Azure DevOps, the org, and the project. A pipeline name is optional. If any of those three is missing, it stops and asks. Options only. It does not guess. It does not ask for a typed path. It reads pipeline definitions with `az pipelines` and `az devops` (list and show only). It does not run, queue, edit, approve, or trigger a pipeline. It does not read builds, logs, test runs, boards, or repo files beyond the pipeline definition. Secrets are not printed. The stage name gives the environment, with the same whole-word rule as `/crav1-environment-read`. A deploy step marks the resource it names. The group is context. The rest of the group is not marked. It appends only confirmed lines to `docs/environments/marks.md`. It creates that file only after at least one confirmed line. It never rewrites an existing line. It does not write `docs/system`, `docs/architecture/spec.md`, a feature spec, or `docs/architecture/left-out.md`. If `az` is missing, the `azure-devops` extension is missing, or there is no login, the stop names which. It does not install or log in. It is a later skill. It is not a starter option. When the user asks for startup options, name only the seven. That ask names the list and does not run this command. The seven starter options stay unchanged. It does not start Specify, Plan, or Build. It names `/crav1-environment-read` and does not run it. Name `/crav1-finalize-commit` when a file changed. Do not run it.
- `/crav1-keep-current` is cross-cutting. It updates that same picture when something was added: the short description, the diagram, and how the parts connect. It adds what is new and does not rewrite what is already there. When this run reads a whole repo, it sets that repo's `Synced at` cell and touches only those repos. When this run reads only one slice, it leaves the column alone and writes the slice line. It does not design the change and does not build it. It can be run on its own. The same passes that already append a new glossary row (spark, ideas, intake, match, and any sibling that already does that append) also run this picture update. They do not rewrite existing glossary rows. Spark, ideas, intake, match, match-dump, code-into-specs, and repos-to-spec update the picture in their own pass and are not asked. An ask does not run this command. Name `/crav1-finalize-commit` when a file changed. Do not run it.
- After tightening, `/crav1-resolve-questions` to keep or answer each remaining Open question.
- When the spec is accepted, `/crav1-plan-from-spec` writes `plan.md` and `tasks.md`. Do not code in that step. Each task verify note names the checks. The plan also says whether this repo has a linter or checker for the code those tasks will touch. When it has one, the plan names it and Build is expected to leave that check green. When it does not, the plan says so and stops before Build. The user decides to add the linter or to go on without one. Do not install one. Specify stays yes/no acceptance and does not name the linter. Optional: `/crav1-review-plan` then `/crav1-tighten-plan` (plan `P#`s only; do not edit `spec.md`). Those two use the same linter rule when they check that a plan is complete.
- Build with `/crav1-implement-task` (one `T#` per turn) or `/crav1-complete-task` (isolated worker for that `T#` through commit → verify → optional fix). Several `T#`s on **one** spec: `/crav1-complete-tasks`. Several **specs**, one after another: `/crav1-complete-features` (serial `feat/<slug>` from default; not parallel). When a slice is marked done or retired, `/crav1-complete-features` asks once whether to run `/crav1-keep-current` and does not run it. `/crav1-implement-task` and `/crav1-complete-task` do not ask. Persist commit style as a rule (same as finalize-commit onward) before the first worker. Prove a slice alone with `/crav1-verify-spec`. Before **live** verify (Aspire/API host, compose, browser localhost), refresh the running resource per `crav1-verify-spec` `references/live-host.md`; do not mark pass on a stale host.
- After `/crav1-verify-spec`, `/crav1-fix-from-verify` with **no Gap** walks the inner-loop queue: verify failed → claimed/unverified → `G#`. Not unimplemented tasks. Do not edit `spec.md`. `/crav1-fix-live` is the same queue with a live-path hint. When the fix changes how the parts connect, it asks once whether to run `/crav1-keep-current` and does not run it.
- Prefer editing the spec or plan over long patch-prompt threads when implementation drifts.
- For a paste-ready GitKraken Summary/Description, `/crav1-draft-commit-message`. It asks CRAV1 style vs live git log, this commit only vs onward (writes a host persist rule — Cursor `.cursor/rules/draft-commit-style.mdc` or `draft-commit-gitlog.mdc`, Claude Code `.claude/rules/` or `~/.claude/rules/` with the same stems; delete that file to undo). Do not commit unless they asked. When `docs/specs/<slug>/work-item.md` exists, the mention is the last description line.
- To change the wording and then `git commit` (no push) or copy for GitKraken, `/crav1-finalize-commit` (`commit` is the first/top choice). Keep that mention through the HEAD check and the Cursor-attribution strip.
- To push the change branch and open one pull request (no merge, no commit), `/crav1-open-pr`. Push only after an explicit yes. GitHub uses `gh`; Azure DevOps uses `az repos pr create` when the CLI is available; otherwise it prints commands and GitKraken GUI paste fields. On Windows, pass a multi-line Azure DevOps description as `--description "@<file>"` (UTF-8 without BOM) so `cmd.exe` does not keep only the first line, then delete the file. Quote `--query` values that contain parentheses. Workers stay no push / no PR. Add a Work item section only when `work-item.md` exists. Do not pass `--work-items`. It may name `/crav1-review-pr` as an optional next step and does not run it. Merging is `/crav1-merge-pr` in a later turn, and only when that turn names the pull request.
- The user points at code that already exists, one repo or one area, not the whole system: `/crav1-suggest-tests-for-code`. It may run from any lane. It reads that code and suggests tests for what that code can actually break. A function gets a few checks. A page gets a browser check. A boundary gets an integration check. It does not dump every test type. Every suggestion stays listed. Nothing is dropped to keep the list short. The user takes them one at a time: keep, leave, or dismiss. Dismiss means it is not offered again. A kept suggestion goes onto the existing spec through `/crav1-add-to-spec`. Plan turns it into a task. It does not write the tests, change the code, or start Specify, Plan, or Build. It does not move work into a lane. It is a later skill. It is not a starter option. When the user asks for startup options, name only those seven. That ask names the list and does not run this command. The seven starter options stay unchanged. Spark, specify, plan, and verify do not run it.
- One feature, slice, resource, or not-yet-feature, when the job is status or what is pending: `/crav1-whats-known-about`. It may run from any lane. The answer comes from the specs first. It reads only. It writes nothing. An exact name match runs first, across spec titles, `tasks.md`, Match quotes, `docs/system/`, `docs/architecture/spec.md`, and `docs/environments/marks.md`. A sentence uses the key words, with spec titles and Match quotes weighted highest. One pass. It does not hunt the whole codebase. An `@` keeps the search inside that path. One slice that wins is the answer, and the path is named. Two or more close hits are listed, one line each, and it asks which. It does not guess. No slice: it says so, shows what the repo, the code, and the environment notes know, and presents a candidate slice. It names `/crav1-spark-to-spec`, `/crav1-ideas-to-spec`, or `/crav1-intake-to-specs` and does not run them. Pasted minutes or a long dump names `/crav1-meeting-to-specs` or `/crav1-match-dump-to-specs` and stops. After the repo part it runs read-only live checks: Azure resource settings and recent changes with `az`, and Azure DevOps work items, open pull requests, and branches that touch the thing. Each live fact is tagged as a live read. Production follows the `/crav1-environment-read` rule: shape and connections only, after the same yes or no. It never reads data. A failed live read shows one prompt with the issue, a fix when there is one, and Retry or Skip. Skip is the repo-only answer, with a line that the live checks did not run and why. A focus still runs the full read and shows only those sections. A code-only hit fills in Unexplained. It may name one skill. It does not run another skill. It does not start Specify, Plan, or Build. It does not move work into a lane. It is a later skill. It is not a starter option. When the user asks for startup options, name only those seven. That ask names the list and does not run this command. The seven starter options stay unchanged. It is not `/crav1-explain`. Explain reads `docs/system/` first. When the picture has nothing on the question, it quotes the first paragraph of a matching spec, labelled as coming from the spec, and names `/crav1-whats-known-about`. It does not run that skill. Spark, specify, plan, and verify do not run it.
- Minutes, a transcript, an email, or a chat thread, when the job is to match items against specs that already exist: `/crav1-meeting-to-specs`. It may run from any lane. Everything after the command, and every `@`, is that input. An email or a chat thread is accepted as well as minutes or a transcript. If there is no pointer, it stops and asks. Options only. It does not guess. The kind is `meeting`, `email`, or `chat`, from what the input shows. If the kind is not clear, it asks once per run, options only. The date comes from the input. It does not invent one. When the input shows no date, it asks once per run, options only: give a date, or skip. A date the user gives is used. Skip means no date. One kind and one date apply to every item. It extracts requirements, decisions, changes, open questions, and bugs. Each item is a quote. It includes the speaker and the time when the input shows them. It drops small talk and status chatter. It matches each item against existing `docs/specs/<slug>/` folders and skips `_template`. The cases are an addition to a named existing spec, a possible new feature, a bug, or unclear. When more than one existing spec could fit, it lists every candidate. It does not drop an item to keep the list short. Each item that matches an existing spec shows one line, `State: <state>.`, and a short reason that names the evidence, in the item block and in the question. The states are built, partly built, planned, and not built. `Fits: none` has no state line. Evidence is that slice’s `spec.md` (including `## Match`), `plan.md`, `tasks.md` checkboxes, and `verify.md` when present. When those do not settle it, one read-only look at the code that spec or plan points to. A code-based or uncertain state is labeled `(inference, not in the docs)`. The line does not change keep, leave, or dismiss. It is not written and it is not passed to `/crav1-add-to-spec` as quote text. The user takes them one at a time: keep, leave, or dismiss. Dismiss is for this run only. The next run starts fresh. It does not write a dismissals file. A kept addition goes to that spec through `/crav1-add-to-spec`. The handoff passes the kind and the date. The quote starts with `From <kind> <date>.` when there is a date, otherwise `From <kind>.` The impact check still runs there. A kept new feature names `/crav1-spark-to-spec`, `/crav1-ideas-to-spec`, or `/crav1-intake-to-specs` and does not run it. A kept bug names `/crav1-fix-bug` and does not run it. It writes nothing itself. It does not copy the input into the repo. It does not start Specify, Plan, or Build. It does not move work into a lane. It is a later skill. It is not a starter option. When the user asks for startup options, name only those seven. That ask names the list and does not run this command. The seven starter options stay unchanged. Spark, specify, plan, and verify do not run it.
- After a build of a slice already exists, `/crav1-exploratory-test`. It may run from any lane. Pass one learns the slice by using it once. Pass two is no longer careful. It adds randomness: sometimes a double-click, a hover back and forth, repeating an action, or using the same control more than once. It follows what the last action showed. It lasts about as long as the first pass, long enough to provoke bugs, then it stops. That stop is named `matched the first pass`. It stops sooner when the user says stop. That stop is named `the user said stop`. It does not run forever. The user does not set a clock. It writes bugs to `docs/specs/<slug>/explore.md`. It does not write the checks the plan already named. It does not start Specify, Plan, or Build. It does not move work into a lane. A bug it finds is not sent to `/crav1-fix-bug` unless the user says so in that turn. It is a later skill. - To review one named open pull request, `/crav1-review-pr`. Only when this turn names it (number or URL) or clearly asks to review that pull request. Any open pull request, not only a feature branch. If none is named, ask which one and stop. Do not pick the newest. It reads the diff. When the slug has `plan.md`, spec, plan, `verify.md`, the pull request body, and a required green linter must hold before it says ship. When the slug has no `plan.md` or `tasks.md`, the pull request was built outside the kit. That is an info note, not a fix finding. It does not report a missing `verify.md`. It reviews spec fit, the pull request body, the required green linter, and secrets, and it reads the test results the pull request's own pipeline already recorded. That test note is info: which tests ran, whether they passed, and which changed files no test touches. The skill does not run tests and does not ask to. When the pipeline shows no test run, the note names the tests the pull request includes and tells the user they can run them manually and then rerun the review. A rerun only sees results the pipeline recorded, so a local run shows up only if the user pastes its output. The note states that these are the pull request's own tests, not a check against the spec. An outside pull request ends by naming `/crav1-keep-current` as the next step after the merge, to bring its changes into the spec and `docs/system/`, and does not run it. A pull request that has a plan keeps the plan and `verify.md` checks. Each miss on the checks that apply is its own finding (what is off, what could happen, decision ship, fix, or drop). Any fix or drop means it does not say ship. It names the lane and does not start it. A body mismatch stays on that pull request. It does not edit code, the spec, or the plan. It does not run the tests, vote, post a comment, install a linter, change branch protection, or merge. Suggestions do not block ship. A secret in the diff is a first-section fix. A clean review says so and stops. Spark, specify, and verify do not run it. A review is not a merge ask.
- To merge one named pull request, `/crav1-merge-pr`. Only when this turn explicitly asks (number or URL). One parent stops the skill. If `az` is missing, the update fails, or a branch policy disallows that merge type, print the REST PATCH and the web UI steps. Do not squash, rebase, bypass policy, delete the branch unless asked, or change work-item links. Do not run `/crav1-review-pr`. A review is not a merge ask.
