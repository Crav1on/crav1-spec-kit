# crav1-help: status

Read only when the pointer in `SKILL.md` sends you here. Moved word for word from `SKILL.md` in 1.71.0; the rules are unchanged.

### 6. Status of a slice

`status <slug>`, or `where am I`. For `where am I`, use the slice the user is working in, or the only one under `docs/specs/`; ask which when there are several.

1. Read the slice's files only: `spec.md` (open questions and their marks), `plan.md` (the `Reviewed:` line and `## Risks`), `tasks.md` (ticks and `(after: T#)`), `verify.md`, and `work-item.md`. Never read Azure Boards.
2. Count tasks with the readiness rules of `/crav1-tasks-ready-to-build` (its `SKILL.md` next to this one): ready, blocked, needs verify, done. Do not repeat the per-task list; for that, name `/crav1-tasks-ready-to-build`.
3. **Branches (1.64.0).** When the spec has work branches (its `Synced at` lines, Match `Branch:` list and task `(branch: …)` parts, minus base branches and `(dropped)` entries), give the Branches line from skill `crav1-add-to-spec`, `references/branches.md`: per repo, how many are merged into the base, each unmerged branch's own commits since its fork point, `merged, branch deleted`, `branch rewritten since last read`, `unknown (branch gone)`, `(also in <slug>)`, and the age of each remote copy in whole calendar days, counted as that file says under **Which refs** (1.67.1: a commit made today is `today`, not `1 day old`). This is read-only git on the refs on disk (and `../<repo>` for another repo); never fetch, never check out, never write. Host checks only for GitHub (`gh`) or Azure DevOps (`az`) when already signed in. For `where am I` across several slices, a shared branch is counted once. **Sub-branches and reverts (1.68.0).** As that file says under **Spec branch and sub-branches** and **Reverted**: sub-branches (entries with `(into <spec branch>)` under a `(spec branch)`) are left out of the Branches count and get `Sub-branches: <n> of <m> merged into <spec branch>.`, plus `left behind: <branch> (not in <spec branch>)` for one that never merged after the spec branch reached the base; done counts top-level branches only. A merged branch whose change was later undone on the base shows `<branch>: merged, reverted on <base> (<revert sha>)`. Both are report only and never block done. **Promotion (1.69.0).** When the spec repo has `docs/environments/promotion.md`, add the `Promotion:` line after the Branches line, as skill `crav1-add-to-spec`, `references/branches.md` says under **Promotion**: per repo, the furthest environment reached and each later one not yet reached, as `on the branch that deploys to <env> (<branch>)` or `not yet on the branch that deploys to <env> (<branch>)`, release patterns as `on release/<x> (deploys to <env>)`, tag lines as `in tag <tag> (deploys to <env>)` or `not yet tagged`, the chain at the end, `Unclear:` for an unknown word with no `(after …)`, and `<branch>: not back on <base>` for a release fix. Branch reach, never `deployed to`. When a pipeline-sourced line is behind it, end with **Also check the latest pipeline runs?** (**Check pipeline runs** / **No, keep the git answer**); the choice word `pipeline runs` runs the check without asking; headless without it gives the git answer plus `Pipeline runs not checked. Add the word: pipeline runs.` Azure DevOps only, read-only; `az has no login` keeps the git answer. Report only: done stays merged into the base.
4. Name the route (`workflow.yaml`) the slice is on and the step it is at, marked from the files: for example no `plan.md` is before Plan; `plan.md` with no `Reviewed:` line is at review-plan; ready tasks are at build; all tasks ticked and verified is at finalize-commit, or at `/crav1-open-pr` / `/crav1-merge-pr` when some work branches are not merged yet.
5. Give the next step from that route, and why. Do not run it.
