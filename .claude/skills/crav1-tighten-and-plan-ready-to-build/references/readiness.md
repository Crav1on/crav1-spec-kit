# Step 7, ready to build

Before this check reads or writes, fetch the specs repo (1.151.0). Behind or diverged: stop, and Run next is `git pull --no-rebase`. A task with someone else's `In progress:` line in `claims.md` is held `in progress by <user> since <date>` and is not offered in Run next. Your own claim does not hold it (1.160.0): the ending says `T5 is yours; the walk resumes it.` A task whose branch's `build-progress/<branch>.md` ends at step `comment` or `wait-merge` is pushed and waits on a merge (1.171.0): it is `waiting`, not in `can_start`, not offered in Run next, and the ending says `Waiting: PR 71 to merge, then T5 is ticked.` and, when it is yours, `T5 is yours and waits for PR 71's merge.` When your task is on a branch whose pull request is open and not merged, at any other step, the ending says `T30 is yours and waits for PR 85's merge.`, never `the walk resumes it` (1.198.0). Tasks that wait on it are held too.

Read this only at the ready check.

When a playbook was named, do not run this check until that question is answered. Resume may already have reported status.

A jump back opens the owning skill's file from this skill's folder and follows it. The rule is [open-skill-file.md](../../crav1-docs/reference/open-skill-file.md) (1.134.0). This check does not open `/crav1-tasks-ready-to-build`. Needs verify is named and its file stays closed.

It runs `task_order.py` and `question_blocks.py`, builds the rows, adds the `Reviewed:` warnings, and writes `build-map.md` in the same format as the standalone command. Print the script's `reply` as the reply, word for word (1.176.0): it is `ending` plus the closing lines, `Source:`, `Build map:` and `Zoom the map in your browser:` with its command. Never stop at the end of `ending` and never drop those closing lines, on the first run or a rerun. `ending` already contains each held line, the one Run next block when tasks can start (led by a `**Catch up first**` block when verify.md or the specs repo is behind, 1.167.0), any Loop line, the Waiting lines, and at most the one-line `/crav1-build-tasks` alternative. Never write a `Next:` line of your own (1.153.0). Keep the `**Catch up first**` block exactly as printed, bold heading and each command alone in its code span (1.196.0), as `crav1-docs/reference/run-ending.md` says. Do not say `above`, `listed above`, or earlier output. Do not point at a list that was only in tool output. Do not hand-build a rows JSON file. Do not pass `--json`. Do not open that skill's file. Use the script's step and command for each row. Do not invent a step the script leaves unmapped. Say the script has no step for it, and do not report ready.

When `question_aliases` is not empty, print one line per entry: `Same question: "<text>" kept as "<matched>". Say this is new to split it.` If they say this is new, run the check again with `--new-question <key>` from that entry. A `Blocks:` line still holds its tasks.

Row buckets: `waits-in-order` is a task that only waits on an earlier real task. `waiting` is a task held by an open question. `blocked` is a true blocker only (a cycle, an `(after:)` that names no task, a missing plan or tasks file, a plan risk, or a question that is still a jump back).

Ready means the first task can start, the rest wait in order, and nothing else blocks. A reason `waits on T#` for a real task is not a hit. A cycle, or an `(after:)` that names no task, is a blocker.

**ready-partial (1.132.0).** The script's `result` is `ready`, `ready-partial`, or `not-ready`. `ready-partial` means `can_start` is not empty and some tasks are held. `not-ready` is when `can_start` is empty, and also when a hard hit is still open. A cycle, a missing task, no plan, an open assumption, a reopened step other than resolve-open-questions alone, or a question that is still a jump back records `not-ready`. Since 1.137.0 a reopened resolve-open-questions step alone does not force `not-ready` when `can_start` is not empty. The result stays `ready-partial`. Print `resolve_waiting` and the resolve line in `next`. When later steps are reopened by a real content change, the result is `not-ready` and `Run next:` names the first of those steps (1.163.0). Since 1.169.0 Needs verify holds only its own task: with `can_start` not empty the result is `ready-partial` and the ready branch blocks still print; with nothing that can start it is `not-ready`. Questions that are not asked yet stay a Run next entry, `/crav1-show-or-ask-open-questions <slug>`, after the branch blocks.

**Loops (1.154.0).** When two or more branches wait for each other, `ending` has one `Loop:` line per loop. It names the branches and the task line behind each direction of the wait. Since 1.161.0 the fix offer follows: `Recommended fix (say `fix-loop`): …`, then each `Other fix (say `fix-loop <n>`): …`, in plain words, and a ready or ready-partial ending adds the Run next entry `/crav1-tasks-ready-to-build <slug> fix-loop`. The open tasks on those branches are Blocked in the counts and in `build-map.md`, from the same judgement. Tasks on other branches keep their own state, so the result can still be `ready-partial`. Print the Loop and fix lines as they are. The fix is applied with `walk_progress.py fix-loop --root <spec-folder> --pick <n>`, a card, then `--yes` (skill `crav1-tasks-ready-to-build`, `references/loop-fix.md`). Never ask the user to edit `tasks.md` by hand.

**can_start while not-ready (1.138.0, 1.163.0).** A hard hit forces `not-ready` and still lists tasks whose bucket is ready in `can_start`. Those tasks wait until the first real next step finishes. The `ending` starts with a `Run next:` entry for that step: a label line, then the command alone in a code span, for example `T5 waits until the reopened /crav1-tighten-plan step finishes:` above `/crav1-tighten-plan <slug>` when the plan was reopened for review (1.173.0; `T5 and T9 wait until ...` for several tasks). There is no build Next line. It still prints each held line. `because` is the same plain reason, for example `The plan was reopened for review, so T5, T9 and T43 wait until /crav1-tighten-plan finishes.`, or the question when a row says it blocks the whole slice (`Holds the whole slice.` on `held_lines`, and `can_start` is empty). A checkbox tick or a `(PR n)` on a branch line is not that hit. Those edits leave the result `ready-partial` when some tasks can start and some are held. Do not ask to clear steps for them.

**By branch (1.133.0).** The `ending` prints each `held_lines` entry. Do not flatten them into `Ready: T1, T2`. Each line is one build-map branch, in wave order, then the map's row order. The branch is the name `scripts/build_map.py docs/specs/<slug> --recommend T#` (skill `crav1-tasks-ready-to-build`) prints. A task is `T#` plus its short name. A held task names its open question and who has the answer, or `held, waits on T3`. Who is the person on the question that started the hold. When the result is `ready-partial`, the script's `line` is those groups. One branch is still one group.

**Ending (1.150.0).** Ask the record card first, then print `reply` as the final reply (1.171.0, 1.176.0: `ending` plus its closing lines): the last reply of the check starts with at most one lead sentence and then `Run next:`, never a prose list of what can start. When `record_unchanged` is true, there is no card: say `Record unchanged.` in the lead and print `reply`. Print `reply` once, not the raw tool output and then the ending again. No person's name and no `the questions haven't been asked yet` recap before Run next; the held lines and Waiting lines say who. Before it, at most one short lead sentence of recap, for example `The plan review is done.` No longer recap, and nothing else before `Run next:` (1.164.0). Run next is one block per ready branch, and the reply ends with `Zoom the map in your browser:` and `/crav1-tasks-ready-to-build <slug> open-map`, as `run-ending.md` says (1.164.0). On `ready`, `ready-partial`, and `not-ready`, `Run next:` is first, before any Waiting line. Each ready entry is a label line, then the command alone in a code span on the next line, never a lowercase line under the command (1.176.0). The command is a complete invocation for a new session: the command and each `T#` on that branch. When `docs/specs` has more than one slice, or this folder is not that single slice, the command also names the slug, for example `` `/crav1-build-walk orders-api T3` ``. One slice under `docs/specs` needs no slug: `` `/crav1-build-walk T3` ``. Nothing else is on that line. It does not use this chat. The label above it names the full task name and the branch, for example `Build T3 Record the decision on feat/orders-api-record:`. Since 1.155.0 each ready branch offers the next task, `` `/crav1-build-walk orders-api T3` ``, and, when the branch has two or more open tasks, the whole branch as its own entry, `` `/crav1-build-walk orders-api feat/orders-api-record` `` under the label `Run the whole branch:`. A branch with one open task gets only the T# entry. The walk command appears only in that Run next block. A `Branch runs:` block lists each whole-branch run recorded in `walk-progress.md` that is not merged, for example `- feat/orders-cicd: running, T9 done, next T10 (log: build-progress/feat--orders-cicd.md)` (1.155.0). Print it as part of `ending`. The bottom keeps any Loop line, the Waiting lines, and at most the one line `/crav1-build-tasks builds one task without the walk.` There is no `Next:` line, and the reply never adds one (1.153.0). Do not run either command. Held lines are in that same reply, under `Held:`. Do not say `above`, `listed above`, or earlier output.

A reopened walk step is a blocker, except a reopened resolve-open-questions step when `can_start` is not empty (1.137.0), and except a reopened `tasks-ready-to-build` step (1.150.0). Running this check reads the current spec, plan, and tasks, so that step's own staleness is cured. It is not a blocker and it is not in `reopened`. When it was the only reopened step, `replaced` is `The earlier tasks-ready-to-build record is replaced.` That sentence is already in `ending`. Say it once. Then the normal record confirm. Do not offer jump back or clear for that step. The result is `ready`, `ready-partial`, or `not-ready` from the rows. Another reopened step still blocks. The script names it and sets `clear` to `nothing new`. Offer jump back and rerun that step (Recommended) only when `recommend_jump` is true, or clear it. The script maps:

- An open question: Open `../crav1-resolve-open-questions/SKILL.md` (`/crav1-resolve-open-questions`), unless that question has a `Blocks:` line, including `Blocks: whole slice`, was already recorded as waiting, or the hold was inferred from `T#` ids in its text (1.137.0). `Blocks: whole slice` holds every unfinished task and the line says `Holds the whole slice.` Then the row is `waiting`, not a jump back. A new or unparsed question jumps back only for the tasks it holds. Who comes first from the question's own "Waiting for <who>" phrase, then from the latest `Pending:` or `Asked:` line. When neither names anyone, who is `not named yet` in the JSON, and that task still counts in `waiting_line`. Since 1.170.0 a hold with nobody named says so plainly: `Nobody is named to answer it yet.` for a question, `Nobody is named to give it yet.` for an approval, and `nobody named for 1` on the Waiting line, never `Waiting for not named yet`. `can_jump_back` is false on a waiting row. Do not mark that jump back Recommended. It cannot change anything.
- An unapproved `## Approval needed` item (1.141.0): the tasks on its `Holds:` line are `waiting` on that person. Other tasks still start (`ready-partial`). A matching `Approved:` line clears the hold. This is not a jump back to resolve. A live `apply` still needs the user's own yes in that build run, and the task stays unticked until then.
- A plan risk, a cycle, or an `(after:)` mark that names no task to step 6, starting at Open `../crav1-tighten-plan/SKILL.md` (`/crav1-tighten-plan`) after Open `../crav1-review-plan/SKILL.md` (`/crav1-review-plan`) when the review line is missing.
- A plan-review warning (`plan review unknown`, or open `P#`) as an assumption, not as ready. The ready skill still lists those tasks as Ready with a warning. This walk does not. An open assumption is not a clear check.
- **Needs verify** names `/crav1-verify-build-against-spec`, and a task whose verify failed names `/crav1-fix-build-gaps <slug> T#` (1.169.0), with a short reason from its Verify cell (1.170.0). That skill is outside this walk. Name it, do not jump into it, do not start it, and do not open its file. This walk never writes `verify.md`.

**verify.md behind (1.136.0).** `readiness --root` compares `tasks.md` with `verify.md`. Merged means the task line, or the Match `Branch:` line for its `(branch:)` or `(map:)` branch, contains `(PR n)` and the word `merged`. There is no host check. A merged task stays done for dependents and for `can_start`. `verify_behind` is true when a ticked task is still `Not implemented`, when an older next line in `verify.md` names a ticked task whose own row is not current (1.169.0: a Verified or Failed row is current), or when a merged unticked task is still `Not implemented`. A merged unticked task whose status is `Implemented, verified, tick pending` is not behind. The tick is the only leftover. Since 1.167.0 the ending shows it as the `**Catch up first**` block at the top of Run next (`catch_up` in the JSON), before the branch blocks: `verify.md is behind for T2.`, then `Check T2 against the spec:` and `` `/crav1-verify-build-against-spec orders-api` ``. They are no longer Waiting lines. `verify_waiting` stays in the JSON. Do not print `stale_next`. `trust_stale_next` is false.
