# Step 7, ready to build

Read this only at the ready check.

When a playbook was named, do not run this check until that question is answered. Resume may already have reported status.

A jump back opens the owning skill's file from this skill's folder and follows it. The rule is [open-skill-file.md](../../crav1-docs/reference/open-skill-file.md) (1.134.0). This check follows Open `../crav1-tasks-ready-to-build/SKILL.md` where this file does not say otherwise. Needs verify is named and its file stays closed.

Run `scripts/walk_progress.py readiness --root <spec-folder>`. Pick the interpreter as `crav1-docs/reference/running-scripts.md` says. It runs `task_order.py` and `question_blocks.py`, builds the rows, and adds the `Reviewed:` warnings. Do not hand-build a rows JSON file. Do not pass `--json`. Use the script's step and command for each row. Do not invent a step the script leaves unmapped. Say the script has no step for it, and do not report ready.

Row buckets: `waits-in-order` is a task that only waits on an earlier real task. `waiting` is a task held by an open question. `blocked` is a true blocker only (a cycle, an `(after:)` that names no task, a missing plan or tasks file, a plan risk, or a question that is still a jump back).

Ready means the first task can start, the rest wait in order, and nothing else blocks. A reason `waits on T#` for a real task is not a hit. A cycle, or an `(after:)` that names no task, is a blocker.

**ready-partial (1.132.0).** The script's `result` is `ready`, `ready-partial`, or `not-ready`. `ready-partial` means `can_start` is not empty and some tasks are held. `not-ready` is when `can_start` is empty, and also when a hard hit is still open. A cycle, a missing task, no plan, Needs verify, an open assumption, a reopened step other than resolve-open-questions alone, or a question that is still a jump back records `not-ready`. Since 1.137.0 a reopened resolve-open-questions step alone does not force `not-ready` when `can_start` is not empty. The result stays `ready-partial`. Print `resolve_waiting` and the resolve line in `next`. When later steps are reopened by a real content change, `next` is `Next: rerun or clear <steps>.` and the result is `not-ready`.

**can_start while not-ready (1.138.0).** A hard hit forces `not-ready` and still lists tasks whose bucket is ready in `can_start`. Those tasks are not a start. Do not print `ready_lines` or a build Next line. Print `because`. It names the reopened steps, or the question when a row says it blocks the whole slice (`Holds the whole slice.` on `held_lines`, and `can_start` is empty). A checkbox tick or a `(PR n)` on a branch line is not that hit. Those edits leave the result `ready-partial` when some tasks can start and some are held. Do not ask to clear steps for them.

**By branch (1.133.0).** Print the script's `ready_lines` and `held_lines`. Do not flatten them into `Ready: T1, T2`. Each line is one build-map branch, in wave order, then the map's row order. The branch is the name `scripts/build_map.py --recommend T#` prints. A task is `T#` plus its short name. A held task names its open question and who has the answer, or `held, waits on T3`. Who is the person on the question that started the hold. When the result is `ready-partial`, the script's `line` is those groups. One branch is still one group.

A reopened walk step is a blocker, except a reopened resolve-open-questions step when `can_start` is not empty (1.137.0). The script names it and sets `clear` to `nothing new`. The check is not ready while any other step is reopened. Offer jump back and rerun that step (Recommended) only when `recommend_jump` is true, or clear it. Clear is the one line `nothing new`. On that, run `clear --step <id> --yes`, then run this check again. Do not record `nothing-to-do` for a reopened step. When the step was `done`, a `nothing-to-do` record keeps `done`.

The script maps:

- No `plan.md` or no `tasks.md`: Open `../crav1-plan-from-spec/SKILL.md` (`/crav1-plan-from-spec`).
- An open question: Open `../crav1-resolve-open-questions/SKILL.md` (`/crav1-resolve-open-questions`), unless that question has a `Blocks:` line, including `Blocks: whole slice`, was already recorded as waiting, or the hold was inferred from `T#` ids in its text (1.137.0). `Blocks: whole slice` holds every unfinished task and the line says `Holds the whole slice.` Then the row is `waiting`, not a jump back. A new or unparsed question jumps back only for the tasks it holds. Who comes first from the question's own "Waiting for <who>" phrase, then from the latest `Pending:` or `Asked:` line. When neither names anyone, who is `not named yet`, and that task still counts in `waiting_line`. `can_jump_back` is false on a waiting row. Do not mark that jump back Recommended. It cannot change anything.
- An unapproved `## Approval needed` item (1.141.0): the tasks on its `Holds:` line are `waiting` on that person. Other tasks still start (`ready-partial`). A matching `Approved:` line clears the hold. This is not a jump back to resolve. A live `apply` still needs the user's own yes in that build run, and the task stays unticked until then.
- A plan risk, a cycle, or an `(after:)` mark that names no task to step 6, starting at Open `../crav1-tighten-plan/SKILL.md` (`/crav1-tighten-plan`) after Open `../crav1-review-plan/SKILL.md` (`/crav1-review-plan`) when the review line is missing.
- A plan-review warning (`plan review unknown`, or open `P#`) as an assumption, not as ready. The ready skill still lists those tasks as Ready with a warning. This walk does not. An open assumption is not a clear check.
- **Needs verify** names `/crav1-verify-build-against-spec`. That skill is outside this walk. Name it, do not jump into it, do not start it, and do not open its file. This walk never writes `verify.md`.

**verify.md behind (1.136.0).** `readiness --root` compares `tasks.md` with `verify.md`. Merged means the task line, or the Match `Branch:` line for its `(branch:)` or `(map:)` branch, contains `(PR n)` and the word `merged`. There is no host check. A merged task stays done for dependents and for `can_start`. `verify_behind` is true when a ticked task is still `Not implemented`, when the verify next line names a ticked task, or when a merged unticked task is still `Not implemented`. A merged unticked task whose status is `Implemented, verified, tick pending` is not behind. The tick is the only leftover. Print `verify_waiting` when `verify_behind` is true, for example `Waiting: /crav1-verify-build-against-spec orders-api - verify.md is behind tasks.md (T2)`. Do not print `stale_next`. `trust_stale_next` is false. That stale file is not Needs verify, and it does not make the result `not-ready`. The result stays `ready` or `ready-partial`, and `verify_waiting` is shown when verify is behind. A ticked task with no verify row, or claimed unverified, or verify failed, stays Needs verify. The ready check still rewrites `build-map.md` by following Open `../crav1-tasks-ready-to-build/SKILL.md`. A spec finding no longer pauses the walk before this check. A change to `verify.md` alone does not reopen this check. Spec, plan, or tasks drift still does. Only the walk's record or `clear --yes` restamps `walk-progress.md`. `/crav1-tasks-ready-to-build` only writes `build-map.md`.

When the script says the check is not ready, print `because` and name each row's step in the words the script returns. Do not say the tasks in `can_start` can start. Offer to jump back only for rows with `can_jump_back`. Options: jump back (Recommended) when `recommend_jump` is true, clear with `nothing new` when a walk step is reopened by a real content change, or stop. A progress-only edit does not reach this question. On jump back, open the owning skill's file and follow it, even for a small patch, then run this check again. The walk does not edit `spec.md`, `plan.md`, or `tasks.md` on a jump back, and it does not write `Reviewed:`. That line belongs to `/crav1-review-plan`. On `nothing new`, clear only the step just named. A row that cannot jump back stays named. The check is still not ready.

When the only rows are `waiting` and `result` is `not-ready`, do not offer jump back. The stop ending adds the script's `waiting_line`: `Waiting: <n> tasks wait on open questions (<who>).` Next is the script's `waiting_next`: `/crav1-show-or-ask-open-questions <slug>` when the questions are not asked yet, or this walk when the answers arrive.

When `result` is `ready-partial`, do not offer jump back and do not record `not-ready`. The walk ends. Record `Result: ready-partial`. The script stamps `Done`. That record covers this step, and earlier steps already recorded stay covered. Print each of the script's `next_lines`, one per ready branch: `Next: /crav1-build-tasks T2 T5 T6` (on `feat/orders-api-record`). Do not join them into one Next line. Do not run them. A later rerun, after the answers are in the spec and resolve-open-questions is current again, moves the held tasks to ready and can record `Result: ready`.

Ready is only when the script says `result` `ready` and `start_build` is false, with no blockers, no waiting, no Needs verify, and no assumptions. Then say the slice is ready to build. Print each `next_lines` entry, one per ready branch. One branch is one line: `Next: /crav1-build-tasks T1` (on `feat/orders-api-record`). Do not run it. Add the Uncommitted line when `walk-progress.md` is not committed. Stop.

When they pick stop and the check is not ready, and the rows are not only waiting, `Next` is the first jump-back row's command, because that row blocks ready. Do not list the other rows in the ending. They were already named in the check. This walk still runs a step when they pick jump back, by opening that skill's file and following it.

Record step `tasks-ready-to-build` when this check finishes, one `record` call, with the versions the script stores, including `Verify version:`, after the user confirms the record. Use `Result: ready` when the script says `ready`, `Result: ready-partial` when it says `ready-partial`, and `Result: not-ready` when it says `not-ready`. Do not record `Result: done` for this step. An older `Result: done` still reads as recorded. Resume treats `ready`, `ready-partial`, `not-ready`, and an older `done` as recorded. Do not batch it with other steps. Do not pass `--when`. A later change to `verify.md` does not reopen this check. Only the walk's record or `clear --yes` restamps `walk-progress.md`.
