# crav1 kit

Specs, not chat history, are the source of truth. Put change work under `docs/specs/<change-id>/`. The layout always includes `docs/system/`. Spark and ideas seed a thin landscape when that folder is missing, including `glossary.md`, and do not rewrite an existing one except new glossary rows and the picture update. They fill a missing `glossary.md` when the folder already exists, and append only new rows when the file exists. Intake writes the landscape, including `glossary.md`, and does not skip it. Existing glossary rows are not rewritten. The picture update adds what is new to the short description, the diagram, and how the parts connect, and does not rewrite what is already there. A meaning the source does not state is `to be researched`.

Type `/crav1` to list kit skills. Typical order: spark, ideas, or intake → feature branch (`feat/<slug>` or specify-only `spec/<slug>`) → architecture review → tighten → resolve questions → plan → review-plan → tighten-plan → implement (or `/crav1-complete-task` / `/crav1-complete-tasks` / `/crav1-complete-features`) → verify → fix-from-verify (do not edit `spec.md` in the fix loop). `/crav1-plan-from-spec` names whether this repo has a linter or checker for the code the tasks will touch. When it has one, the plan names it and Build is expected to leave that check green. When it does not, the plan says so and stops before Build. The user decides to add the linter or to go on without one. Do not install one from the plan skill. Specify does not name the linter. `/crav1-spark-to-spec` is greenfield, a brownfield feature, or a later feature on `docs/system/` (new slug unless they extend). It seeds a thin `docs/system/` when that folder is missing, including `glossary.md`, then the spec, then one index row. `/crav1-intake-to-specs` writes the landscape, including `glossary.md`, plus one spec per v0 feature. `/crav1-match-to-specs` matches existing repos plus a dump to the landscape, including `glossary.md`, and one spec per confirmed slice. It does not replace spark, ideas, or intake. `/crav1-match-dump-to-specs` sorts a later dump onto specs that already exist. It does not create a slug. It does not seed `docs/system/`. A missing `glossary.md` is filled only when that folder already exists, and new rows are appended when the file exists. `/crav1-code-into-specs` sorts a code change that already landed onto specs that already exist. No dump is required. It does not create a slug. It does not watch the repo. It does not seed `docs/system/`. A missing `glossary.md` is filled only when that folder already exists, and new rows are appended when the file exists. `/crav1-add-to-spec` adds new information to one existing spec and reports impact on the landscape or other specs before editing them. It does not create a glossary. A new glossary row can be one listed edit. `/crav1-security-review` is cross-cutting. It runs only when architecture already exists (`docs/system/` or a spec that already describes the design). The same command covers the whole system, one existing spec, or the change in front of us. It writes kept findings and stops. It does not plan, implement, or commit. Spark, plan, and verify do not run it. `/crav1-repos-to-spec` is cross-cutting. The user names one or more repos. It reads those repos and writes one architecture spec the lanes can extend at `docs/architecture/spec.md` when that file is missing. The folder is `docs/architecture/`. The file is `spec.md`. That path is locked. It stays out of `docs/system` and out of `docs/specs`. Do not invent any other folder. `docs/specs` stays one folder per feature slug. `docs/system` stays the short picture. When a real note is already in `docs/system/`, it does not rewrite those notes and writes only the missing architecture spec. When `docs/architecture/spec.md` is already there, a later re-read adds only what is new and does not rewrite lines that are already there. The same rule applies to system notes that are already there. When those notes are missing, it writes the `docs/system/` notes `/crav1-explain` reads. A fact the code shows is confirmed. A guess stays out of the spec until the user confirms it. A link between repos is written only when the code shows it. If none is found, it says so. It does not invent links. It does not design the next feature, write application code, or start Specify, Plan, or Build. It is not `/crav1-code-into-specs`. `/crav1-explain` is cross-cutting. It reads `docs/system/` and the first answer is a short TLDR. Longer goes one level deeper from the same notes. The user can point it at one part. A question about whether the system can do something is yes with a pointer, no, or that it is not written down. It does not guess, write a second document, teach, or start Specify, Plan, or Build. When the picture is older than the specs, it says so and names `/crav1-keep-current`. It does not run it. `/crav1-keep-current` is cross-cutting. It adds what is new to the short description, the diagram, and how the parts connect. It does not rewrite what is already there. It does not design the change and does not build it. It can run on its own. Spark, ideas, intake, match, and any sibling that already appends a glossary row also run this picture update in that same pass. They do not rewrite existing glossary rows. `/crav1-review-pr` is cross-cutting. It runs only when the user names an open pull request in that turn, or clearly asks to review that pull request. It reads the diff and names the lane for a finding. It does not edit code, the spec, or the plan, and it does not vote, comment, install a linter, or merge. Spark, specify, and verify do not run it. `/crav1-open-pr` may name it and does not run it. `/crav1-merge-pr` does not run it. A review is not a merge ask. `/crav1-fix-bug` is cross-cutting. It runs only when the user names a real bug. If they have not named one, it stops. It does not go hunting. A real bug is a verify failure on work that is already shipping, or a defect that comes in from outside. A design gap found before Build stays in the spec. An unfinished task stays a task. A one-off flaky check is a note, unless it keeps blocking ship. It says where the bug was seen (verify, a report, or production), names the bug, points at the spec or the shipped behavior it breaks, and names the lane. A spec miss goes to Specify. A plan miss goes to Plan. A verify miss or a broken implementation goes to Build. It does not start that lane, edit code, open a pull request, or create an Azure Boards work item. It is not a lane and not a stretch of verify. When the user asks for startup options, it is one of the options in that list. It is an intake for a bug that already exists. It is not a skill that runs because a repo is new, and it is not started automatically. Spark, specify, plan, and verify do not run it.

Do not scaffold an application unless the user asked for one. Prefer editing the spec or plan when implementation drifts.

Full install paths: `docs/install.md` in the kit repo. After a plugin install, start with the plugin README.

On Claude Code this file is the project instruction (`.claude/CLAUDE.md`). A user-scope install uses the same text in `~/.claude/CLAUDE.md` and does not commit the kit into a client repo. Playbook paths that start with `.claude/` are the project drop-in. If that file is not in the repo, read the same path under `~/.claude/`.
