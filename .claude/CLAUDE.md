# crav1 kit

Specs, not chat history, are the source of truth. Put change work under `docs/specs/<change-id>/`. The layout always includes `docs/system/`. Spark and ideas seed a thin landscape when that folder is missing, including `glossary.md`, and do not rewrite an existing one except new glossary rows and the picture update. They fill a missing `glossary.md` when the folder already exists, and append only new rows when the file exists. Intake writes the landscape, including `glossary.md`, and does not skip it. Existing glossary rows are not rewritten. The picture update adds what is new to the short description, the diagram, and how the parts connect, and does not rewrite what is already there. A meaning the source does not state is `to be researched`. `docs/system/repos.md` has a per-repo `Synced at` column, `<branch>@<short sha>, <date>`. A repo may list several branches, separated by `; `. Example: `main@abc1234, 2026-10-07; develop@def5678, 2026-10-06`. When `/crav1-keep-current`, `/crav1-repos-to-spec`, `/crav1-code-into-specs`, or `/crav1-intake-to-specs` and `/crav1-ideas-to-spec` (where they read repos) read a whole repo, they set that repo's column to the branch and commit they actually read. They touch only the repos they read. When a run reads only one slice, it does not touch the repo column. It writes or updates `Synced at: <repo> <branch>@<short sha>, <date>` in that slice's `spec.md`. A consumer measuring drift uses the older of the repo column and the slice line, and an empty value means unknown, so fall back to spec file commit dates.

When the user asks for startup options, name only these seven: `/crav1-spark-to-spec`, `/crav1-ideas-to-spec`, `/crav1-intake-to-specs`, `/crav1-match-to-specs`, `/crav1-repos-to-spec`, `/crav1-environment-read`, and `/crav1-fix-bug`. Every other skill is a later skill. That ask names the list. It does not run a skill and does not move work into a lane. Each starter still follows the rules it already has. `/crav1-repos-to-spec` still runs only when the user names repos. `/crav1-environment-read` still runs only when the user names the host. Naming production, prod, or live stops. `/crav1-fix-bug` still runs only when the user names a real bug.

Type `/crav1` to list kit skills. Typical order: spark, ideas, or intake → feature branch (`feat/<slug>` or specify-only `spec/<slug>`) → architecture review → tighten → resolve questions → plan → review-plan → tighten-plan → implement (or `/crav1-complete-task` / `/crav1-complete-tasks` / `/crav1-complete-features`) → verify → fix-from-verify (do not edit `spec.md` in the fix loop). `/crav1-plan-from-spec` names whether this repo has a linter or checker for the code the tasks will touch. When it has one, the plan names it and Build is expected to leave that check green. When it does not, the plan says so and stops before Build. The user decides to add the linter or to go on without one. Do not install one from the plan skill. Specify does not name the linter. `/crav1-spark-to-spec` is greenfield, a brownfield feature, or a later feature on `docs/system/` (new slug unless they extend). It seeds a thin `docs/system/` when that folder is missing, including `glossary.md`, then the spec, then one index row. `/crav1-intake-to-specs` writes the landscape, including `glossary.md`, plus one spec per v0 feature. When it quotes a mail, a transcript, a chat, a screenshot, or another original, it writes `docs/sources/YYYY-MM-DD-<slug>/` following the imported-sources convention. It does not commit. `/crav1-match-to-specs` matches existing repos plus a dump to the landscape, including `glossary.md`, and one spec per confirmed slice. When it quotes a mail, a transcript, a chat, a screenshot, or another original, it writes `docs/sources/YYYY-MM-DD-<slug>/` following the imported-sources convention. It does not commit. It does not replace spark, ideas, or intake. `/crav1-match-dump-to-specs` sorts a later dump onto specs that already exist. When a confirmed quote comes from a mail, a transcript, a chat, a screenshot, or another original, it writes `docs/sources/YYYY-MM-DD-<slug>/` following the imported-sources convention. It does not commit. It does not create a slug. It does not seed `docs/system/`. A missing `glossary.md` is filled only when that folder already exists, and new rows are appended when the file exists. `/crav1-code-into-specs` sorts a code change that already landed onto specs that already exist. No dump is required. A whole-repo read sets that repo's `Synced at` cell. A one-slice read writes the slice line and does not touch the column. It does not create a slug. It does not watch the repo. It does not seed `docs/system/`. A missing `glossary.md` is filled only when that folder already exists, and new rows are appended when the file exists. `/crav1-add-to-spec` adds new information to one existing spec and reports impact on the landscape or other specs before editing them. An imported mail, transcript, chat, screenshot, or other original is written under `docs/sources/YYYY-MM-DD-<slug>/` before the quote, following that skill's `references/sources.md`. It does not commit. It does not create a glossary. A new glossary row can be one listed edit. A kept addition from `/crav1-meeting-to-specs` is handed here. The impact check still runs. The environment-read and suggest-tests-for-code handoffs ask once at the end of the run, not per item, whether to run `/crav1-keep-current`, and do not run it. `/crav1-security-review` is cross-cutting. It runs only when architecture already exists (`docs/system/` or a spec that already describes the design). The same command covers the whole system, one existing spec, or the change in front of us. It writes kept findings and stops. It does not plan, implement, or commit. Spark, plan, and verify do not run it. `/crav1-repos-to-spec` is cross-cutting. The user names one or more repos. It reads those repos and writes one architecture spec the lanes can extend at `docs/architecture/spec.md` when that file is missing. The folder is `docs/architecture/`. The file is `spec.md`. That path is locked. It stays out of `docs/system` and out of `docs/specs`. Do not invent any other folder. `docs/specs` stays one folder per feature slug. `docs/system` stays the short picture. When a real note is already in `docs/system/`, it does not rewrite those notes except the `Synced at` cell of a repo this run read, and writes the missing architecture spec and `docs/architecture/left-out.md`. When `docs/architecture/spec.md` is already there, a later re-read adds only what is new and does not rewrite lines that are already there, except that `Synced at` cell. It also reads `docs/architecture/left-out.md` and removes a line when the code shows it. The same rule applies to system notes that are already there. When those notes are missing, it writes the `docs/system/` notes `/crav1-explain` reads. A fact the code shows is confirmed. Before any file is written, it confirms in sections, one question each: one per named repo, inferred guesses, links, and left-out. Every item stays listed. A guess stays out of the spec until that section accepts it, and then it is accepted from a guess, not a code fact. A guess that stays left out is written to `docs/architecture/left-out.md`. The left-out answer can accept a line, keep it left out, or dismiss it. Dismiss means it is not offered again. A link between repos is written only when the code shows it. If none is found, it says so. It does not invent links. Confirming a guess does not turn it into a link. It does not design the next feature, write application code, or start Specify, Plan, or Build. It is not `/crav1-code-into-specs`. `/crav1-environment-read` is cross-cutting. The user names the host at the start. It still runs only when the user names the host. Naming production, prod, or live stops. It does not guess the host. It never reads production data. One pass reads every non-prod environment. Each seen line keeps its own environment. Each host has its own reader. This build has readers for Azure, AWS, and Google Cloud. Any other host stops with no reader and does not pretend to read it. It does not read Azure DevOps, GitHub, or CI. The user names the host, not the subscription, the account, or the project. Marks come from the name, the group, the tags, and `docs/environments/marks.md` when that file exists. Pre-prod, a resource shared with prod, and a prod-only resource are shape and connections only, after one yes. Prod-only means the only mark is production. A no lists them as not read, and a declined prod-only resource stays skipped. A line from that yes says `prod only`. The skill appends only confirmed lines to `docs/environments/marks.md`. It does not write `docs/system`, `docs/architecture/spec.md`, a feature spec, or `docs/architecture/left-out.md`. A fact is seen in that environment, not something the code shows. It does not become a link unless the environment shows the connection. After the first read, and before any section, it can look inside a database or storage when the user says yes. SQL is metadata only. Storage is structure only. It never reads a row or a blob. Production databases and production storage are never opened. A prod-only shape read does not open them. A database with no clear environment is asked before it is opened. It does not install a tool, and it does not create a login, a firewall rule, a role, or a key. Confirmation is one section at a time. After the user confirms a section, the skill that already owns the file adds only what is new. It does not rewrite a line that is already there. It does not start Specify, Plan, or Build. After `docs/environments/marks.md` lines are added, it asks once whether to run `/crav1-keep-current` and does not run that refresh from the question. `/crav1-pipeline-environments` is cross-cutting. The user names Azure DevOps, the org, and the project. A pipeline name is optional. If any of those three is missing, it stops and asks. Options only. It does not guess. It does not read builds, logs, test runs, boards, or repo files beyond the pipeline definition. Secrets are not printed. The stage name gives the environment, with the same whole-word rule as `/crav1-environment-read`. A deploy step marks the resource it names. The group is context. The rest of the group is not marked. It appends only confirmed lines to `docs/environments/marks.md`. It creates that file only after at least one confirmed line. It never rewrites an existing line. It does not write `docs/system`, `docs/architecture/spec.md`, a feature spec, or `docs/architecture/left-out.md`. If `az` is missing, the `azure-devops` extension is missing, or there is no login, the stop names which. It does not install or log in. It is a later skill. It is not a starter option. When the user asks for startup options, that ask names the seven and does not run this command. The seven starter options stay unchanged. It does not start Specify, Plan, or Build. It names `/crav1-environment-read` and does not run it. `/crav1-explain` is cross-cutting. It reads `docs/system/` and the first answer is a short TLDR. It does not guess, write a second document, teach, or start Specify, Plan, or Build. An ask does not run `/crav1-keep-current`. `/crav1-review-pr` is cross-cutting. It runs only when the user names an open pull request in that turn, or clearly asks to review that pull request. The skill does not run tests and does not ask to. An outside pull request ends by naming `/crav1-keep-current` after the merge and does not run it. It is an intake for a bug that already exists. It still runs only when the user names a real bug. It is not a skill that runs because a repo is new, and it is not started automatically.
